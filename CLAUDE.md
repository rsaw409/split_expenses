# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flutter client for "Split Expense," a group expense-splitting app (Android, iOS, web, desktop). It talks to a separate backend service; there is no backend code in this repo.

## Commands

```bash
flutter pub get                 # install dependencies
flutter run                     # run on a connected device/emulator
flutter analyze                 # static analysis (flutter_lints, see analysis_options.yaml)
flutter test                    # run all tests in test/
flutter test test/unit_test.dart -n "should add two numbers together"  # run a single test
flutter build appbundle         # Android release build (used by CI)
```

## Architecture

**State management**: `provider` with `ChangeNotifier`, wired up once in `lib/main.dart` via a `MultiProvider`. Views read/watch controllers with `context.watch`/`context.read`/`Selector` rather than passing state through constructors.

- `SettingsController` — theme mode (`ThemeMode.system` / `light` / `dark`, default `system`), persisted to `SharedPreferences` as `'system' | 'light' | 'dark'`.
- `GroupsController` — list of joined groups and the currently selected group, persisted to `SharedPreferences`. Groups/selected group are stored as raw `Map<String, dynamic>` (not the `Group` model) once saved.
- `BackendReachability` (`notify_controllers/backend_reachability.dart`) — polls every 10s with a `HEAD` to `server` (`services/server.dart`), pausing while the app is backgrounded (`WidgetsBindingObserver`) and resuming on `AppLifecycleState.resumed`. Two deliberate details: it probes **the app's own backend, not google.com** (reachability of Split's server is what governs whether anything works; a third-party probe wrongly reports offline on networks that block it, on captive-portal wifi, or when DNS is flaky — each time disabling every write), and **any HTTP response counts as reachable**, including the 404 the base URL returns, since only the fact that something answered matters. The backing field is **nullable with the getter defaulting to `true`**: "not probed yet" must not read as offline, or every cold start flashes an offline banner before it has checked anything. Naming and copy follow that reality: the getter is `isReachable`, and user-facing text says "Can't reach Split" rather than "You're offline", because a failed probe genuinely cannot tell a dropped connection from a server that is down. `HomeView` shows a slim banner above the tab content (not a full-screen swap) when unreachable; the FAB stays fully usable (see "Write gating when unreachable" below).
- `AllExpenseController` / `UserBalanceController` — thin subclasses of `CachedListController<T>` (`lib/src/notify_controllers/cached_list_controller.dart`), which owns the entire cache-first load state machine once; each subclass only supplies its fetch/cache functions and its two user-facing message strings. Declared with `ChangeNotifierProxyProvider2<GroupsController, BackendReachability, _>` and only rebuilt (full refetch) when the selected `groupId` actually changes, not on every `GroupsController` change. Exposed state: `isLoading`, `isError` + `errorMessage`, `isStale`, `items` (plus an `expenses`/`userBalances` alias), and `refresh()`, which returns a `Future`. **Every pull-to-refresh calls `refreshGroupData(context)`** (`utils/refresh_group.dart`), which refreshes both controllers and completes once both have, so the spinner lasts the real duration. Wiring a `RefreshIndicator` to a single controller's `refresh` left the other screen's data stale (pulling on the overview kept an old transaction list). The notification handler in `HomeView` uses it too. **Empty and failed screens are pullable as well**: they wrap their `EmptyStateView`/`ErrorView` in `PullToRefreshState` (`components/async_state.dart`), and their Retry calls `refreshGroupData` too. An empty or failed list is exactly when someone wants to check again, and returning the bare state in place of the list used to leave nothing to pull. Only "No group yet" isn't wrapped, having nothing to refresh. Invariants worth preserving when editing `CachedListController` (each is covered by `test/cached_list_controller_test.dart`, and each test has been checked to fail without its guard):
  - **Never notify after dispose.** The provider disposes a controller the moment the selected group changes, but its in-flight fetch outlives it. `_notify()` is the single choke point for this; adding a bare `notifyListeners()` call reintroduces a debug-mode crash on group switch.
  - **Only the newest load may publish.** Dart futures can't be cancelled and responses can arrive out of order (pull-to-refresh overlapping an automatic refresh), so each load captures a `_requestId` and abandons its result if a newer load has started.
  - **No selected group is an empty state, not an error.** `groupId == null` leaves `isError` false and fetches nothing; the views render an onboarding `EmptyStateView` ("No group yet") for it. Routing it through `ErrorView` put a red error icon on a first-run user's opening screen.
  - **`_hasData` is not `items.isNotEmpty`.** A group with genuinely zero expenses has loaded successfully, so a later failed refetch must keep showing the empty state rather than flipping to `ErrorView`.
  - **Refresh on the unreachable→reachable edge, not on `isStale`.** Losing the backend without attempting a fetch leaves data un-stale yet outdated, so `onReachabilityChanged` tracks the transition instead. It defers via `scheduleMicrotask` because the provider calls it from inside `update()`, where notifying synchronously would fire mid-build.
  - **One bounded retry after a failed fetch while reachable.** Observed on a real emulator: the fetch fired the instant the backend came back and failed while the radio was still associating, and since no further transition followed, that list stayed stale indefinitely while the other one refreshed. `_scheduleRetryIfReachable` covers exactly that window; it is not re-armed until the next success or reachability edge, so a genuinely down backend is never hammered and nothing retries while it is unreachable.

**Networking** (`lib/src/services/`): plain `http` package calls, no codegen/client abstraction.
- `server.dart` holds the single backend base URL (commented-out `localhost` line for local backend development).
- `backend.dart` — expenses/payments/user-balance endpoints. `fetchExpenses(groupId, userId, byId, isPayments)` supports three server-side filters, but **the app always passes `null` for all of them** and reproduces the filtering client-side over the cached list instead (see "Per-user transaction lists" below); the parameters are kept only because they document real endpoint capability. Expenses are create-only from the client's perspective — there is no edit/delete endpoint, only `saveTransaction`/`savePayment`/`savePayments` (all POST/create) — which is what makes them safe to cache indefinitely (see "Local caching" below). `fetchExpenses` always returns the full list for a group; there's no cursor/incremental-fetch param. If that's ever added backend-side, it should be a new param (**not** `byId`, which already means something else) — e.g. `since_transaction_id` — so the client can merge deltas instead of replacing its local cache wholesale on every fetch.
- `group_service.dart` — group creation and invite-based join. **Joining** (`views/join_group_view.dart`) accepts a bare invite id, the shared link, or a message containing the link: `inviteIdFromInput` (`utils/invite_link.dart`) extracts and decodes the id, since a shared link carries its `/` as `%2F`. Joining needs no idempotency key (rejoining just returns the group), and the form says "already in" when the group was already saved locally. **`createGroup` is one atomic request** carrying `name`, `currency`, `members` (names) and an `idempotency_key` (form-scoped `IdempotencyKey`, as for expenses), and returns the group plus `currency` and `members: [{user_id, name}]`. Verified against the live backend on 2026-09-28: replaying a key returns the original group (same id and members; `inviteId` differs, as on every join), even with a different payload. The server rejects duplicate member names (case-insensitively) and blank members, but **accepts a blank group name, any currency code (e.g. `USD`), and a single member** — the client form is what enforces a name, INR only, and at least two people, and it trims the group name (the server trims member names only). Old clients sending only `{name}` still get an empty INR group. There is no `leaveGroup` backend call — leaving a group (`GroupsController.removeCurrentGroup()`) is purely local/client-side state.
- **Timeouts** — every HTTP call is bounded, using `readTimeout` (15s) and `writeTimeout` (20s) from `server.dart`. Reads fail benignly, since cache-first paint keeps what is on screen and flips `isStale`, so they give up sooner; writes wait longer because abandoning one that may already have committed is worse, and retrying is safe anyway given the idempotency key below.
- **Write idempotency** — all three writes carry an **`idempotency_key` in the request body**, never a header: a payment is a transaction too, so they share one transport, and it matches how the rest of this API passes everything as body fields. `saveTransaction`/`savePayment` take a required `idempotencyKey` param and the service merges it into the body, so a call site cannot forget it. `savePayments` instead expects **every payment in the array to carry its own key** (the service asserts this), because per-item keys are what let a retry after a *partial* failure re-apply only the payments that did not land — a single key per request would only be safe if the server applied the batch atomically. Keys come from `lib/src/utils/idempotency.dart`: `IdempotencyKey` for single writes, scoped to a **form session** — stable across retries of the same payload, reissued when the payload changes, cleared only on success — and `IdempotencyKeySet` for batches, memoising a key per item identity (`from`/`to`/`amount` for settle-up; safe because the settlement walk advances both indices monotonically, so one debtor never pays the same creditor twice in a batch). **The server honours this** — verified end-to-end on 2026-09-23: repeating a `saveTransaction` or a `savePayments` element with the same key returns the original row (same id *and* same `createdAt`), while the same content under a different key creates a new row, so dedupe keys on the key rather than on matching content. `savePayment` was not exercised. Note the wire format itself is not covered by a test — the service calls top-level `http.post` with no injectable client, so there is nothing to mock. `reset()` is never called on failure, which is what makes a retry safe without swallowing an edited resubmission. The three write call sites also distinguish `ApiException` (server answered, nothing committed → report its message) from any other error (no response → the write *may* have landed, so refresh the controllers and show `unconfirmedWriteMessage` rather than implying a clean failure). `test/idempotency_test.dart` pins the key lifecycle.
- `api_exception.dart` — `apiExceptionFrom(response, fallback, {useServerMessage = true})` builds the error. **Pass `useServerMessage: false` for endpoints whose failure messages aren't fit for users** — `joinGroupFromInviteId` does, because a mistyped invite code comes back as a raw Node crypto error (`The "buffer" argument must be of type string...`) under a **400**, so the status cannot distinguish a helpful validation message from a leaked internal one, and the old code showed it verbatim in a SnackBar. Note nothing tests that a given call site passes the flag: the services call top-level `http.post` with no injectable client, so only the helper itself is covered. Every function throws `ApiException` (not a generic `Exception`) on a non-200 response; `apiExceptionFrom(response, fallback)` tries to pull a `message`/`error` field out of the JSON body and falls back to a plain-English default otherwise. `ApiException.toString()` returns just the message (no `"Exception: "` prefix), so it's safe to show directly in a `SnackBar`/`ErrorView`. Still no shared HTTP client wrapper or retry logic.

**Member pickers** (`lib/src/utils/members.dart`): the "Paid by", split, and payment from/to pickers build their options with `membersFromBalances(UserBalanceController.userBalances)` — the `getAllUsersInGroup` endpoint is no longer called at all, and its `getUsersInGroup` wrapper has been deleted (recover from git history if ever needed). `User` is consequently an in-memory-only model with no `fromMap`/`fromJson` — nothing deserialises a member any more.

This rests on a property **verified against the live backend, not guaranteed by contract**: `getOverviewDataInGroup` returns a *complete* member list, including someone just added who has no transactions (they come back with a zero balance and zero counts). If that ever changes, newly added members silently disappear from the pickers that record expenses — the failure is silent, not loud, so `test/members_test.dart` states the assumption explicitly and `getAllUsersInGroup` is the endpoint to reach for. The forms also fire an unawaited `refresh()` in `initState`, so options paint instantly from cache and update if someone was added elsewhere; on a cold start with no cache the pickers stay hidden until it lands, exactly as they did while the old request was in flight.

**Member avatars** (`utils/avatar.dart`, `components/member_avatar.dart`): a member's avatar is a **seed string** for `random_avatar` (multiavatar), which draws the same face from the same seed every time. It is chosen when the member is added — the add-person form and each create-group chip show a random face that can be reshuffled — and sent as `avatar` to `createUser` / in each `createGroup` member (`{name, avatar}`). The backend saves it (nullable column; refuses blank or over 64 characters, verified 2026-09-29) and returns it from `getOverviewDataInGroup` and `createGroup`; there is **no endpoint to change it**, so once saved it is fixed. Members from before avatars have `null` and keep exactly the look they had: initials (`MemberAvatar`'s fallback), and the person icon on the member screen. Expenses don't carry avatars, so screens that show split members look them up by `user_id` from `UserBalanceController`. **`random_avatar` is pinned to an exact version** in `pubspec.yaml`: stored avatars are only seeds, so a release that changed the drawing algorithm would silently change every face — check that before bumping it.

**Group icons** (`utils/group_icon.dart`, `components/group_icon.dart`): an emoji on a coloured circle, saved by the backend as `icon` (the emoji) and `icon_color` (a palette **key** such as `teal`, not a hex value, so each theme resolves its own shade). The backend requires the two together, refuses blanks, and caps them at 32 bytes / 20 characters, but **does not restrict which emoji or colour** — the app owns the catalogue (`groupIconEmoji`, Emoji 11 or earlier so none render as boxes on older Android; `groupIconColors`), so it can grow without a server change, and an unknown key falls back to the first colour. `createGroup` sends a random icon the user can change in the picker (emoji grid, colour row, Cancel / Done — Cancel keeps the previous icon); `updateGroup` sends it only when changed, and counts as a change on its own; `getGroups` and `joinGroup` return it, so `applyServerGroups` spreads a change to other devices at launch. Verified live 2026-09-29. Groups from before icons have neither field and keep their initials. `Group.toMap()` **leaves the keys out when there is no icon**: writing `icon: null` made every pre-icon saved group compare unequal to its fetched self, so each launch notified and rewrote them (`test/groups_controller_test.dart` caught it).

**Write gating when unreachable** (`lib/src/utils/reachability.dart`): there is no write queue — every mutation needs the backend, so writes are blocked in two layers. `requireReachable(context, message:)` guards the request itself and is called in **every** write path (`new_expense.dart`, `new_payment.dart`, `settle_view.dart`, `new_form.dart` for person/join/create, and `HomeViewState.handleInvite` for deep-link joins) — keep it even where the button is already disabled, because reachability can drop while a form is open and pushed routes don't carry `HomeView`'s banner. `watchIsReachable(context)` drives the UI layer: being unreachable disables "Settle up" (`overview_view.dart`). Controls that only **open a form** are deliberately **not** gated: the drawer's + button (its New group / Join group dialog) and all three FAB options (New person / payment / expense) always open their form, and the form's submit-time `requireReachable` reports the problem while keeping what the user typed, so they can retry once back online. (Gating the drawer also fought the layout: a permanent caption cluttered it, and `Scaffold` paints the drawer over snackbars.) Reads and local-only actions (switching groups, leaving a group, theme) stay available regardless — leaving is ungated on purpose, since `removeCurrentGroup()` makes no backend call.

**Per-user transaction lists** (`lib/src/utils/expense_filters.dart`): `UserView`'s Expenses / Payments / Benefits-from rows open `ExpensesView`, which used to issue its own filtered `fetchExpenses` call per tap (a loader every time, broken offline). It now filters `AllExpenseController.expenses` in memory via `filterExpenses`, so those screens need no network at all. The predicates were **verified against the live backend** — for every user in a test group they returned the same transaction ids as the filtered endpoint and reproduced its `number_of_transactions`/`number_of_payments`/`number_of_benefits` counts, including the case where a received payment counts as a benefit:
- Expenses → paid by the user, excluding payments (`userId == id && !isPayment(e)`)
- Payments → paid by the user, payments only
- Benefits from → user appears in `distributions` (payments **not** excluded)

`isPayment()` lives here too and is the single definition of what a payment is: **`transactionCategory == 'payment'`**, the server's own field, exposed by `getAllExpensesInGroup` as `transaction_category` (note the write endpoints echo the same thing as plain `category` — the read and write names differ). `expense_tile.dart` and `single_expense_view.dart` both route through it, so nothing can drift apart. The old `transactionTitle == 'payment'` heuristic survives in exactly one place — `Expense.fromMap`, and only when the `transaction_category` **key is entirely absent**, which means a cache entry written before the field existed. A key that is *present and null* is authoritative, so a fresh expense titled "payment" stays an expense. That distinction is what lets the shim exist without reinstating the bug it replaced; without it, payments already on disk degrade to "payment / \<payer\>" rows with the wrong icon until a refetch, which was observed on a device that could not reach the backend. The shim disappears on its own as cache entries are rewritten. `test/expense_filters_test.dart` pins all of this against the real backend's numbers. The counts shown in `UserView` still come from `UserBalance` (the backend), not from these predicates.

**Total expenditure** (`views/total_expenditure_view.dart`, opened from the home three-dot menu) totals `AllExpenseController.expenses` client-side via `computeExpenditure` (`utils/expenditure.dart`), so it works offline. A person's cost is their **share of each split** (`distributions`), not what they paid — which is why it is unaffected by pending settle-up payments — and payments are excluded entirely, since counting them would double-count the spending they settle. The donut is a hand-rolled `CustomPainter` rather than a chart package, to keep the bundle small.

**Amounts are integers in the group currency's minor unit, end to end** (`lib/src/utils/currency.dart`) — paise for INR (₹120.50 → `12050`), cents for USD, whole yen for JPY (0 decimals), fils for KWD (3 decimals). The backend stores `BIGINT` minor units; it rejects fractional amounts and requires a transaction's parts to sum *exactly* to `totalAmount`. So every model field (`Expense.transactionAmount`, `Distribution.amount`, `UserBalance.balances`), every write payload, the split sheet and settle-up all hold `int` minor units, and all arithmetic is exact integer math whatever the currency. Decimals exist only at the UI edges, all on `Currency`: `parse` for what the user types (parsed as text, never through a double, and refusing more decimals than the currency has), `format`/`toText` for display, `inputPattern` for the input filters. Screens get the selected group's currency with `context.groupCurrency` (`utils/group_currency.dart`, called in `build`); the split sheet is handed it by the expense form. `supportedCurrencies` deliberately includes JPY and KWD so nothing can quietly assume two decimals — the yen split test and the currency tests in `test/amounts_test.dart` pin that. Never do arithmetic on doubles: that's what made the old `DOUBLE`-rupee backend reject valid splits (166.67 ×4 + 166.66 ×2 summed to `999.9999999999999` in Node). `UserBalance`'s `number_of_*` counts are ints too (the backend's INT8 parser made them numbers). This was a breaking API change shipped together with the backend: a pre-paise app build sends rupees, which a paise backend would store 100× too small.

**Local caching** (`lib/src/services/cache_service.dart`): per-group `SharedPreferences` JSON blob cache for expenses and balances (`getCachedExpenses`/`setCachedExpenses`/`getCachedBalances`/`setCachedBalances`, plus `clearGroupCache`) — public wrappers over generic `_readList`/`_writeList` helpers, so adding another cached resource means one more wrapper, not another copy of the JSON plumbing. Reads are deliberately fault-tolerant: a cache entry that no longer parses (corrupt, or written by a build whose model shape has since changed) is **deleted and treated as a miss** rather than thrown, because an unguarded `fromMap` cast here would otherwise wedge the screen on every launch with no way to self-heal. Keep that try/catch if you touch this file. `CachedListController` reads the cache on cold start only (paint instantly if present, skip the full-screen spinner), then always still hits the network — on success the cache is overwritten and `isStale` clears; on failure, if data has already loaded (from cache or a prior fetch) it's kept and `isStale` is set instead of `isError`, so the UI degrades to "last known data" rather than blanking. This is a whole-list overwrite cache (matches the "backend always returns everything" networking model above), not an incremental/queryable store — if the backend ever gains a cursor param, or if list sizes grow enough to matter, revisit this as a real local DB (sqflite/drift) with per-row upserts, not just a drop-in storage-engine swap behind the same function signatures. Cache keys carry a version (`cache_v2_…`), bumped when the *meaning* of a cached field changes and not only its shape: rupee-era entries can parse cleanly (a whole-rupee `100` is a valid int) and would read as ₹1, so the parse-failure self-heal is not enough. `dropStaleCaches()` (called unawaited from `main`) deletes other-version `cache_` keys. `GroupsController.removeCurrentGroup()` calls `clearGroupCache` so a left group's cached data doesn't leak into a future rejoin.

**Models** (`lib/src/models/`): immutable `Equatable` classes with hand-written `fromMap`/`toMap`/`fromJson`/`toJson` (originally scaffolded from `models.jsonc` using the "JSON to Dart Model" generator — see that file for the intended workflow if adding new models). Field names in JSON are snake_case; model properties are camelCase.

**Group details and editing**: `Group` carries a `currency` code (`INR` for groups saved before currencies existed) and `currencyDecimals` (`currency_decimals` in JSON). `createGroup` and `updateGroup` must send `currency_decimals` together with `currency` — both build them with `Currency.toApiFields()`, so the decimals always come from `supportedCurrencies`, never from input. That matters because the backend **stores whatever decimals it is sent without checking them** (verified 2026-09-28: INR with 3 was accepted) and formats notification amounts with them; the app itself formats with its own `Currency.decimals`. `utils/currency.dart` defines `Currency` (code, name, symbol, decimals) and `supportedCurrencies` (INR only; the backend refuses others), shared by the create and edit forms through `components/currency_field.dart`. A group's currency is stored and shown but does **not** yet change how amounts are entered or formatted — everything is still rupees via `formatPaise`. `GroupsController.refreshGroups` calls `POST /getGroups` on launch and `applyServerGroups` updates saved groups by id (never adding one, so a group left meanwhile stays gone), so a rename or currency change made on another device shows up at next start. A group's currency is chosen freely when creating it, but on the edit page it is **locked once the group has any transaction** (expenses or payments): amounts are stored as a count of the currency's smallest unit, so switching would silently relabel every existing amount (₹100.00, stored as 10000, would read as ¥10,000). The page unlocks it only when `AllExpenseController` has loaded this group's list without error and it is empty; loading, failed or another group's list all count as locked. The backend must enforce the same rule once a second currency exists, since only it knows for certain. `views/edit_group_view.dart` (three-dot menu → Edit group) calls `POST /updateGroup` with only the changed fields (the backend refuses a request with neither); names are capped at 50 characters client-side because the backend sets no limit.

**Navigation**: single named route (`/`) rendering `HomeView`; everything else is pushed imperatively (`Navigator.push`) from within views rather than declared as named routes. Deep links of the form `/joinGroup/<inviteId>` (see "Invite links" below for hosts) are handled in `lib/src/app.dart`, which calls back into `HomeViewState.handleInvite` via a `GlobalKey` to join the group into `GroupsController`. Two traps, both handled by `lib/src/utils/invite_link.dart` and pinned by `test/invite_link_test.dart`:
- **Invite ids are base64-like and often contain `/`** (plus `+`, `=`, `:`). `inviteLink()` builds the shared link, and the invite dialog's QR code, from path segments, so the `/` is percent-encoded. But Flutter **decodes the whole route name** before the app sees it, so `%2F` arrives as a real `/` regardless. `inviteIdFromRoute()` therefore takes *everything* after `joinGroup/`, never just the next segment; the old `pathSegments[1]` silently truncated such ids.
- **Cold starts go through `onGenerateInitialRoutes`, not `onGenerateRoute`.** Navigator's default initial-route handling splits a deep link into one route per path prefix and generates each, so `/joinGroup/a/b` used to run the invite handler for `/joinGroup` and `/joinGroup/a` as well, racing a truncated join against the real one. A deep link arriving while the app is running is pushed as one name and does reach `onGenerateRoute`.
- **`handleInvite` uses `HomeViewState`'s own context**, not one passed in. `app.dart` only has a context above `MaterialApp`, where there is no `ScaffoldMessenger`, so the old signature made every deep-link snackbar throw (success and failure alike) and a join gave no feedback at all.

A group's **invite id is stable**: the backend used to issue a fresh one on every `joinGroup` response (a new IV each time) and now always returns the same id for a group. Ids issued before that keep working.

The QR code is always dark on white (scanners often fail on inverted codes), and is wrapped in a fixed-size `SizedBox` because `AlertDialog` queries intrinsic sizes and `QrImageView` (a `LayoutBuilder`) asserts if asked. **The invite survives the install** via the Google Play Install Referrer: the Play links (`playStoreLink()`, and web/index.html's hand-off) carry `referrer=invite%3D<id, encoded>`, encoded twice because Play decodes it once. On first launch `HomeViewState` calls `takeInstallReferrerInvite()` (`lib/src/services/install_referrer.dart`, plugin `play_install_referrer`) and joins through `handleInvite`. It is marked handled in SharedPreferences (`installReferrerHandled`) as soon as Play answers, invite or not, so a group the user later leaves is never re-joined; if Play errors or times out (10s; the plugin has no deadline of its own), nothing is marked and the next launch asks again. A build installed with adb gets no referrer: this emulator's Play Store answers `FEATURE_NOT_SUPPORTED`. The end-to-end path can only be exercised on a build installed from Play, e.g. the internal testing track, by opening its listing URL with a `&referrer=` parameter. `test/invite_link_test.dart` checks `playStoreLink()` against a Play link captured from the old join page's actual output, so web/index.html's copy of that encoding must stay in step. Debug builds are signed with a different key than the one in `assetlinks.json`, so on a dev device invite links open the browser (whose hand-off still reaches the app, since it's addressed to the package) unless approved with `adb shell pm set-app-links-user-selection --user cur --package developer.rohitsaw.split true split.rsaw409.me`.

**Invite links** are `https://split.rsaw409.me/joinGroup/<id>` (`inviteLinkHost`), on the web app's own site. The app's SHARE text and QR code carry only that link. Where it opens:
- **Android, in order: the Android app, the web app, Google Play.** The Android app claims the links with **App Links** (an `autoVerify` intent filter for `https://split.rsaw409.me/joinGroup/`), verified through `web/.well-known/assetlinks.json`, which the web build copies to the site root and which holds the Play signing key's SHA-256 fingerprint. Where it is installed, Android opens it directly, no browser involved, even if the web app is installed too (to check on a device with both: Chrome's installed web apps also open links to their own site). Without it, Chrome's installed web app opens the link. A link that still lands in a browser tab (nothing installed, or followed inside Chrome itself) meets an inline script in `web/index.html`, before Flutter loads, that applies the same order: `navigator.getInstalledRelatedApps()` says which apps are installed (the `"webapp"` and `"play"` related applications in `manifest.json`; the Android app is only detectable because its `asset_statements` meta-data declares the site). With only the web app installed it stays, and the tab's install screen joins the group, which Chrome's installed web apps see since they share the tab's storage. Otherwise it hands off to `intent://split.rsaw409.me/joinGroup/<id>#Intent;scheme=https;package=developer.rohitsaw.split;…`, which opens the Android app if installed (detected or not) and otherwise follows its `S.browser_fallback_url`, as does a 2s timer for browsers that ignore `intent://`: Google Play with the invite as install referrer. The script does nothing in the installed web app (`display-mode: standalone`). The page keeps loading meanwhile, so coming back to the tab finds the install screen.
- **iPhone/iPad**: iOS opens every link in Safari, even with Split on the Home Screen, and no page can detect the Home Screen app, whose storage is separate. So Safari shows the install screen (see "Browser tabs are blocked") with COPY INVITE for pasting into the Home Screen app's Join group.
- **Computers and other browsers**: the tab shows the install screen. Chromium's installed apps share the tab's storage, so the screen joins the group for them; elsewhere it offers the invite to copy.
- **One domain**: invite links moved from `portfolio.rsaw409.me` on 2026-09-30, with no redirect kept, since Split was still in development. The portfolio repo no longer has anything of Split's, and `inviteIdFromInput` accepts only `split.rsaw409.me` links.
- **Path URLs on web**: `main.dart` calls `usePathUrlStrategy()`. Flutter's default reads the route from the `#` fragment, so the path `/joinGroup/<id>` was ignored and web invite links opened the app without joining. Render rewrites every path without a file to `index.html`, and after handling an invite the address bar returns to `/`, so a reload neither re-joins nor hands off again.
- `index.html` has Open Graph tags and `web/split-og.png` for link previews, which crawlers read without running JS.
- Verified 2026-09-30 in headless Chrome against the production build, backend and Play intercepted, with id `ab/c+d=`: an Android tab with neither app went to Play with `referrer=invite%3Dab%252Fc%252Bd%253D`; the installed web app and desktop Chrome joined with the id intact (before tabs were blocked; since then, an Android tab reporting the web app installed joins from the install screen, and iPhone Safari shows COPY INVITE without joining); (the portfolio's redirect for old links, tested then, has since been removed). The browser hand-off was verified 2026-09-30 on the Pixel 6 API 34 emulator with a debug build: an invite link opened in Chrome brought Split to the front within about 3s, from a cold start too, and it routed the invite (a fake id, so the backend answered "Invalid or expired invite code."). App Links verification can only be checked once `assetlinks.json` is live on `split.rsaw409.me` with a Play-signed build: `adb shell pm get-app-links developer.rohitsaw.split` should report `split.rsaw409.me: verified`.

**Group-scoped UI**: `HomeView` is a two-tab (`Overview` / `Expenses`, opening on Overview) scaffold for whatever group is currently selected in `GroupsController`; switching the selected group cascades through the proxy providers above to refetch overview/expense data.

**Push notifications**: OneSignal is initialized by `initializePush()` from `main.dart`, with the app ID in `services/push_common.dart`; **targeting is by device, managed by the backend, not OneSignal tags.** `GroupsController.registerDevice` (on launch, join, leave, and when OneSignal issues or changes the subscription id) calls `POST /registerDevice` with this install's OneSignal push subscription id and the **group ids** of all saved groups (`services/push_registration.dart`); the server replaces that device's list and sends each group's notifications with `include_subscription_ids`. Plain group ids, a deliberate choice: they are sequential, so anyone could register for any group, but every other endpoint is already keyed by the same unauthenticated id (invite ids were considered and rejected as not making group data any more private). Calls are serialised (the server replaces the list, so out-of-order calls could leave an older one in place) and failures are silent, retried next launch. Tags were abandoned after measuring the plan on 2026-09-28: **6 tags per device**, a request exceeding it refused whole (409 `entitlements-tag-limit`), and additions counted before removals — so at most 6 groups could ever notify a device. Launch removes any leftover `group…` tags. The SDK loads an existing subscription id in the background after `initialize` *without* firing the change observer, so `PushRegistration.subscriptionId()` polls briefly for it. `HomeViewState` (`lib/src/views/home.dart`) registers `OneSignal.Notifications.addClickListener`/`addForegroundWillDisplayListener` in `initState()` (removed in `dispose()`) so a notification arriving or being tapped triggers `AllExpenseController.refresh()`/`UserBalanceController.refresh()` for whatever group is currently selected — this doesn't try to parse a `group_id` out of the notification's `additionalData`, since there's no backend code in this repo to confirm the payload shape; it's a deliberate simplification (worst case: one redundant refetch if the notification was for a different group than the one on screen). This matters more than it used to since the local cache (see "Local caching" above) means the app no longer refetches eagerly on its own — a notification is now one of the few signals that proactively refreshes stale data.

**Web push** uses OneSignal's **Web SDK v16 through JS interop**, because `onesignal_flutter` has no web implementation (still true of 5.7.0; OneSignal closed Flutter web support as not planned). `services/push.dart` conditionally exports `push_native.dart` (the plugin) or `push_web.dart` (`dart:js_interop`, which does not compile for the native apps); both must provide the same functions, and the analyzer only checks callers against the native one, so a mismatch shows up in `flutter build web`. `PushRegistration` and `HomeView` go through these functions, so the registration flow above is shared. Details that matter:
- **Same OneSignal app, no Firebase**: the dashboard's Web platform (Custom Code setup) sits beside Android under the same app ID, and web push uses VAPID keys OneSignal manages. A web subscription id is registered with `registerDevice` exactly like a phone's.
- **Only on `https://split.rsaw409.me`**: a OneSignal app accepts one site origin, so elsewhere (`localhost`, any debug build) the SDK is not even loaded. Testing push locally needs a second OneSignal app configured for `localhost`.
- **Its own worker scope**: the SDK registers `web/push/onesignal/OneSignalSDKWorker.js` at `/push/onesignal/`, apart from `sw.js` at the root. Only one worker can control a scope, push messages reach the registration that subscribed whatever controls the page, and kept apart, a blocked OneSignal CDN can't break `sw.js`'s install. OneSignal recommends exactly this, and requires the file on the site's own origin.
- **Notifications are offered in the installed app only; a browser tab only shows the install screen.** `pushPermission()` reports `unavailable` in any tab, so neither the startup dialog nor the drawer row appears there. In the installed app, installing doesn't grant permission (on iPhone either), so `askForNotificationsOnce` (`components/notifications_prompt.dart`) asks on its first launch. The browser's own prompt appears only after TURN ON: Firefox and Safari (every iPhone browser) ignore a permission request no tap led to, Chrome may quietly hide one shown on load, and a Block in the browser is permanent unless undone in its site settings. `requestPushPermission` runs synchronously inside the tap, making the JS call before anything is awaited once the SDK has loaded, for Safari. It is shown once (`notificationsPromptShown`), whatever the answer, and never over a screen opened while the SDK loaded (the next launch asks instead). Launches with nothing to ask (native, already allowed, blocked, push unavailable) don't count. Afterwards the drawer's `NotificationsAction` row turns them on (hidden once allowed, in tabs and on native). Once blocked, nothing can prompt again, so its "Notifications blocked" row explains where to allow them, which for an installed app is usually outside the browser: iPhone Settings → Notifications → Split, Android App info → Notifications, the app window's App info on a computer, macOS System Settings for a Safari Dock app (`showBlockedHelp`, keyed on the install method). Blocking keeps the same OneSignal subscription id (web push ids never change); OneSignal marks it unsubscribed on the next visit, and the launch-time `registerDevice` is skipped while permission is off. Re-allowing marks it subscribed again on the next visit, and that launch's `registerDevice` sends the current groups, including any joined meanwhile. Notifications switched off at the OS level (e.g. for Chrome on macOS or Windows) can still read as granted, which no web app can detect. iPhone/iPad web push needs iOS 16.4+.
- **Browser tabs are blocked** (`views/install_gate_view.dart`): Split only runs installed, so in a release build a browser tab gets `InstallGateView` instead of `HomeView` (`app.dart`, `blockedInBrowserTab`), with no way past it. `flutter run` serves the app in a tab, so debug and profile builds aren't blocked. "In a tab" is `!matchMedia('(display-mode: standalone)')` (`services/web_app_web.dart`), which relies on the manifest's `"display": "standalone"`; iPhone Safari supports the query from iOS 12.2. A tab doesn't load OneSignal either. `installMethodFor` (`utils/install_method.dart`, pure and unit-tested with real user agents) picks what the screen offers, from Flutter's platform (which detects iPads reporting a Mac) and the user agent: **iPhone/iPad** (any browser but bare in-app WKWebViews): Share, then Add to Home Screen; **Android** (not WebViews, which mark themselves `; wv)`): *Get the Android app* (`playStoreLink()`, carrying the invite through the install referrer) or *Install the web app*; **Chromium on a computer**: INSTALL; **Safari 17+ on a Mac**: File, then Add to Dock; **anything that can't install** (Firefox on a computer, in-app browsers, older Mac Safari): open the page in Chrome, Edge or Safari, with COPY LINK. Chromium's one-tap install uses `beforeinstallprompt`, which fires once and often before Flutter starts, so `flutter_bootstrap.js` keeps it as `window.splitInstallPrompt` (and `preventDefault()`s Chrome's own Android banner); `installPromptAvailable` updates if it arrives later, and without it the screen explains the browser's menu. It never fires once installed, so the screen also says where to open an installed Split. **An invite link that opens in a tab** is passed to the screen instead of `HomeViewState.handleInvite`. Where the installed app shares the tab's storage (Android browsers' and Chromium's installed web apps), the screen joins the group there ("You've joined … It's waiting for you in the app"). Safari's installed apps (iPhone, iPad, Mac) keep their own storage, so there it offers COPY INVITE for Join group → Paste instead of joining. With no invite in the link, the group the browser had selected (from before tabs were blocked) is the one carried over.
- Verified 2026-09-30 in headless Chrome against the production build and a stand-in SDK, emulating each platform (screenshots): browser tabs on iPhone (steps and COPY INVITE, no join), Android (with the web app reported installed: joined the link's group in the background) and desktop Chrome (INSTALL, from Chrome's real `beforeinstallprompt`; accepting opened the prompt) each got the install screen, and Firefox on a Mac got the other-browser variant; the installed iPhone and desktop apps got the app and TURN ON; TURN ON reached `registerDevice`, and NOT NOW left the browser alone and kept the drawer row. Neither prompt asked again.
- **The SDK may never load**: ad blockers commonly block `cdn.onesignal.com`, and offline it can't load. The SDK future resolves to null on a script error or failed `init` (e.g. "App not configured for web push", seen before the dashboard was set up), and callers time out after 15s, so push quietly degrades to unavailable.
- Verified 2026-09-30 in headless Chrome: against a stand-in SDK (init options, listeners, `registerDevice` after a grant, refresh on click and foreground display, the drawer row, both workers registered with `sw.js` still controlling the page), and against the real SDK before web was configured (queue processed, init rejected, degraded quietly). An end-to-end delivery needs the dashboard configured and the deployed site.

**No Firebase in the app** (removed 2026-09-28). It was only ever added for push, and OneSignal doesn't use it: its Android SDK creates its own named Firebase app (`ONESIGNAL_SDK_FCM_APP_NAME`) from FCM credentials fetched from the OneSignal dashboard (the Firebase service-account key for project `portfolio-rsaw409` is uploaded there), and brings `firebase-messaging` in itself. So there is no `firebase_core`, `google-services.json`, `GoogleService-Info.plist` or google-services Gradle plugin, and none should be re-added for push. Invite deep links don't use Firebase either (they are App Links on the web app's domain), nor does web push (VAPID, see "Web push" above). Web builds and runs (see "Web / PWA" below). `flutter run -d macos` fails for an unrelated reason — `macos/Runner.xcodeproj`'s `MACOSX_DEPLOYMENT_TARGET` (10.14, in all three build configs) predates what the installed Xcode/CocoaPods toolchain requires (12.0+); bump the deployment target project-wide to fix. Android is the only platform confirmed working in this environment; iOS wasn't tested here (no simulator available) but has no known issue.

**Web / PWA** (`web/`): the backend sends CORS headers (`Access-Control-Allow-Origin: *`, verified 2026-09-29), and platform-only code is guarded with `kIsWeb` rather than `dart:io` `Platform` (which throws on web): the install referrer and the drawer's Feedback link (Play web page in a browser, `market://` on Android, hidden on iPhone/iPad whether native or web). Push is the exception: it is split at compile time instead (see "Web push"). CI fails the build if anything in `lib/` imports `dart:io`. Offline support is our own `web/sw.js`, because Flutter's `flutter_service_worker.js` is now a stub that unregisters itself. The details that matter:
- **`web/flutter_bootstrap.js` is custom and must not pass `serviceWorkerSettings`**: Flutter's loader re-registers its own worker whenever any worker is registered, which would replace `sw.js` and then delete it. The bootstrap also removes `index.html`'s splash after the first frame, registers `sw.js` in release/profile builds only, and keeps Chromium's `beforeinstallprompt` for the install screen (see "Browser tabs are blocked"). **Debug builds (`compileTarget: dartdevc` in `_flutter.buildConfig`) get no worker**, and they remove one left by a release build served on the same `localhost` port. Unregistering only takes effect once no page uses the worker, and until then it keeps re-creating its cache from the debug session's requests, so the page reloads once, guarded by a `sessionStorage` flag. Note that the first page load after `flutter run -d web-server` starts can stall for a minute while dwds warms up, whatever the browser state; don't mistake that for a worker problem.
- **`sw.js`** handles GETs only, so backend POST/HEAD calls pass through untouched. The app's own files are network-first, so online launches get the latest deploy. The cache fallback ignores query strings (`package_info_plus` cache-busts `version.json`) and also covers a 5xx from the host, but not a 4xx. **Only the shell itself (the scope root or `index.html`) is ever stored as the shell.** Every navigation falls back to it offline, since the app routes whatever path it was opened at, but other in-scope pages are never kept. Otherwise opening `/manifest.json` in a tab once replaced the offline app with that JSON (observed). For the same reason the PWA wants **its own origin**: under a shared domain its scope would take in unrelated pages and assets. **`const BUILD = 'dev';` is stamped by CI** with the release version, so each deploy changes `sw.js`, the browser reinstalls it, and its install step refreshes `PRECACHE`. Without that, files Flutter loads only on first use stay at whatever version was first cached. CI fails if the line is missing, so keep it verbatim. CanvasKit and fonts from gstatic are cache-first, since their URLs are versioned. On install it precaches the shell *and* files Flutter only loads on first use (ink/stretch shaders, asset manifest, drawer logo), because without them the first tap offline threw. Keep `PRECACHE` in step with `pubspec.yaml` assets. The CanvasKit variant and fonts depend on the browser, so the page posts its loaded resource list to the worker. Emoji fonts are cached only once they have been shown online.

Web icons come from `flutter_launcher_icons`' `web:` section; running the tool regenerates Android/iOS icons too, so to touch only web, use a temporary config with `android: false` / `ios: false` via `-f`.

**Theming** (`lib/src/theme/app_theme.dart`): `AppTheme.light` / `AppTheme.dark` build a Material 3 `ThemeData` from `ColorScheme.fromSeed(seedColor: Colors.deepPurple)`, with every component theme set (AppBar, Card, inputs, buttons, chips, dialogs, snackbars, FAB, tabs, etc.) so widgets should pull colors from `Theme.of(context).colorScheme` rather than hardcoding `Colors.*`. `AppSpacing`/`AppRadius` hold the 8dp spacing/radius scale used instead of magic-number `EdgeInsets`. Snackbars are floating app-wide, including on `HomeView`. **Keep the home "+" FAB (`lib/src/components/floating_action_button.dart`) a normal-size button whose menu is a separate see-through route.** It replaced `flutter_expandable_fab`, which lays the closed FAB out full-screen to draw its own overlay: `Scaffold` then placed every floating snackbar above that "FAB", off the top of the screen, so no home-screen snackbar was ever visible. `test/add_fab_test.dart` pins that a floating snackbar lands on screen above the FAB. `ColorScheme` is extended with `.positive` (a brightness-aware green) since M3 has no built-in "success" role — used opposite `.error` for the owed/owes balance coloring in `overview_view.dart`/`user_view.dart`.

**Shared UI components** (`lib/src/components/`): `async_state.dart` (`LoadingView`, `ErrorView`, `EmptyStateView`, and `PullToRefreshState` to keep an empty or error state pullable) is the standard loading/error/empty pattern for list views — pair with a controller's `isLoading`/`isError`/`errorMessage`. `expense_tile.dart` (`ExpenseTile`) is the shared row for both `all_expenses_view.dart` and `expenses_view.dart`. `detail_row.dart` (`DetailRow`) is the label/value row for detail screens (`single_expense_view.dart`, `user_view.dart`). `lib/src/utils/currency.dart` (`formatPaise`) formats amounts as `₹1,234` via `intl` — used everywhere instead of ad hoc `'INR $amount'` string concatenation.

## CI/CD

`.github/workflows/release.yml` (renamed from `android-release.yml`) runs in stages, on push/PR to `main`:
1. **check** — `flutter analyze`, a check that `lib/` doesn't import `dart:io` (it throws on web), `flutter test`, and computing the version.
2. **build-android** (signed app bundle + APK, keystore from secrets), **build-ios** (an **unsigned** build on a macOS runner packaged as an `.ipa` — no Apple signing is configured, so it must be re-signed before it installs) and **build-web** (a release web build for the root of its own origin, base href `/`, with the version stamped into `build/web/sw.js` — see "Web / PWA" — zipped as `split-web.zip`), in parallel.
3. **publish-android** deploys the bundle to the Play Store **production** track (`developer.rohitsaw.split`) as a completed release. **publish-web** force-pushes the web build to the **`web-release`** branch (see "Web hosting" below). **publish-ios** is a placeholder, since App Store publishing isn't supported yet.
4. **github-release** (runs alongside the publish jobs, needing only the builds) publishes a GitHub Release tagged `v<version name>-build<version code>` with the APK, AAB, IPA and web zip attached.

The app bundle is built with `--obfuscate --split-debug-info=build/symbols`; the symbols are attached to the GitHub release as `<name>-aab-symbols.zip` (workflow artifacts expire), and are needed to read its Dart stack traces with `flutter symbolize`. The APK is not obfuscated.

Stages 3 and 4 only run on pushes to `main`. A failed store upload doesn't block the GitHub release.

**Web hosting**: a Render static site serves the **`web-release`** branch at **https://split.rsaw409.me**, and redeploys on every push to it. Its settings live in the Render dashboard, not in this repo: publish directory `public`, a no-op build command, a rewrite `/*` → `/index.html`, and the custom domain (Namecheap DNS: `CNAME split` → the site's `.onrender.com` host). Render applies rewrites only where no file exists, so the catch-all never shadows `main.dart.js` and friends. `publish-web` pushes **one orphan commit holding only the latest build**, so the branch never accumulates history; every build stays attached to its GitHub release. It **never replaces a newer deploy with an older one**: builds from consecutive pushes run in parallel, so it compares its build number against the deployed `public/version.json` and skips if not newer. To roll back, revert on `main` and let the fix roll forward. Render's dashboard rollback also exists, but it switches auto-deploy off until re-enabled. **Nothing in a Flutter web build is content-hashed** (`main.dart.js` keeps its name across builds), so no file may be long-cached. Render's default `Cache-Control: public, max-age=0, s-maxage=300` with ETags is exactly right (browsers revalidate every time, and Render purges its CDN on deploy), so don't add a long `max-age` header.

**Versioning is not fully manual**: builds pass `--build-name=<version name> --build-number=<run number + VERSION_CODE_OFFSET>`, so the `+N` you commit in `pubspec.yaml` is ignored — only the version *name* (e.g. `1.2.4`) needs bumping by hand. The offset (100) exists because the run number counts per workflow *file*: the rename restarted it at 1 after the old file's run #70, and Play rejects a version code that doesn't increase. Renaming the file again means raising the offset past the final run number of the file being replaced.
