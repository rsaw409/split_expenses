# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flutter client for "Split Expense," a group expense-splitting app (Android, iOS, web, desktop). It talks to a separate backend service; there is no backend code in this repo.

## Commands

```bash
flutter pub get                 # install dependencies
flutter run                     # run on a connected device/emulator
flutter analyze                 # static analysis (flutter_lints, see analysis_options.yaml)
flutter test                    # run all tests in test/
flutter test test/unit_test.dart -n "should add two numbers together"  # run a single test
flutter build appbundle         # Android release build (used by CI)
flutterfire configure           # regenerate lib/firebase_options.dart if Firebase project config changes
```

No `flutter format` step is configured (static analysis is `flutter_lints` via `flutter analyze`, which CI does run — see CI/CD below). `test/unit_test.dart` and `test/widget_test.dart` are still the unmodified Flutter project templates; the real coverage lives in `test/cached_list_controller_test.dart` and `test/expense_filters_test.dart`.

## Architecture

**State management**: `provider` with `ChangeNotifier`, wired up once in `lib/main.dart` via a `MultiProvider`. Views read/watch controllers with `context.watch`/`context.read`/`Selector` rather than passing state through constructors.

- `SettingsController` — theme mode (`ThemeMode.system` / `light` / `dark`, default `system`), persisted to `SharedPreferences` as `'system' | 'light' | 'dark'`.
- `GroupsController` — list of joined groups and the currently selected group, persisted to `SharedPreferences`. Groups/selected group are stored as raw `Map<String, dynamic>` (not the `Group` model) once saved.
- `InternetConnectivityHelper` — polls every 10s with a `HEAD` to `server` (`services/server.dart`), pausing while the app is backgrounded (`WidgetsBindingObserver`) and resuming on `AppLifecycleState.resumed`. Two deliberate details: it probes **the app's own backend, not google.com** (reachability of Split's server is what governs whether anything works; a third-party probe wrongly reports offline on networks that block it, on captive-portal wifi, or when DNS is flaky — each time disabling every write), and **any HTTP response counts as reachable**, including the 404 the base URL returns, since only the fact that something answered matters. The backing field is **nullable with the getter defaulting to `true`**: "not probed yet" must not read as offline, or every cold start flashes an offline banner before it has checked anything. Note the public getter is still named `isConnectedToInternet` though it now means "backend reachable". `HomeView` shows a slim offline banner above the tab content (not a full-screen swap) when disconnected, and hides the FAB (writes require connectivity; there's no offline write-queue).
- `AllExpenseController` / `UserBalanceController` — thin subclasses of `CachedListController<T>` (`lib/src/notify_controllers/cached_list_controller.dart`), which owns the entire cache-first load state machine once; each subclass only supplies its fetch/cache functions and its two user-facing message strings. Declared with `ChangeNotifierProxyProvider2<GroupsController, InternetConnectivityHelper, _>` and only rebuilt (full refetch) when the selected `groupId` actually changes, not on every `GroupsController` change. Exposed state: `isLoading`, `isError` + `errorMessage`, `isStale`, `items` (plus an `expenses`/`userBalances` alias), and `refresh()` — which returns a `Future` so `RefreshIndicator.onRefresh` can be wired straight to it and hold its spinner for the real duration. Invariants worth preserving when editing `CachedListController` (each is covered by `test/cached_list_controller_test.dart`, and each test has been checked to fail without its guard):
  - **Never notify after dispose.** The provider disposes a controller the moment the selected group changes, but its in-flight fetch outlives it. `_notify()` is the single choke point for this; adding a bare `notifyListeners()` call reintroduces a debug-mode crash on group switch.
  - **Only the newest load may publish.** Dart futures can't be cancelled and responses can arrive out of order (pull-to-refresh overlapping an automatic refresh), so each load captures a `_requestId` and abandons its result if a newer load has started.
  - **No selected group is an empty state, not an error.** `groupId == null` leaves `isError` false and fetches nothing; the views render an onboarding `EmptyStateView` ("No group yet") for it. Routing it through `ErrorView` put a red error icon on a first-run user's opening screen.
  - **`_hasData` is not `items.isNotEmpty`.** A group with genuinely zero expenses has loaded successfully, so a later failed refetch must keep showing the empty state rather than flipping to `ErrorView`.
  - **Refresh on the offline→online edge, not on `isStale`.** Going offline without attempting a fetch leaves data un-stale yet outdated, so `onConnectivityChanged` tracks the transition instead. It defers via `scheduleMicrotask` because the provider calls it from inside `update()`, where notifying synchronously would fire mid-build.
  - **One bounded retry after a failed fetch while online.** Observed on a real emulator: the fetch fired the instant connectivity returned and failed while the radio was still associating, and since no further transition followed, that list stayed stale indefinitely while the other one refreshed. `_scheduleRetryIfOnline` covers exactly that window; it is not re-armed until the next success or connectivity edge, so a genuinely down backend is never hammered and nothing retries while offline.

**Networking** (`lib/src/services/`): plain `http` package calls, no codegen/client abstraction.
- `server.dart` holds the single backend base URL (commented-out `localhost` line for local backend development).
- `backend.dart` — expenses/payments/user-balance endpoints. `fetchExpenses(groupId, userId, byId, isPayments)` supports three server-side filters, but **the app always passes `null` for all of them** and reproduces the filtering client-side over the cached list instead (see "Per-user transaction lists" below); the parameters are kept only because they document real endpoint capability. Expenses are create-only from the client's perspective — there is no edit/delete endpoint, only `saveTransaction`/`savePayment`/`savePayments` (all POST/create) — which is what makes them safe to cache indefinitely (see "Local caching" below). `fetchExpenses` always returns the full list for a group; there's no cursor/incremental-fetch param. If that's ever added backend-side, it should be a new param (**not** `byId`, which already means something else) — e.g. `since_transaction_id` — so the client can merge deltas instead of replacing its local cache wholesale on every fetch.
- `group_service.dart` — group creation and invite-based join. There is no `leaveGroup` backend call — leaving a group (`GroupsController.removeCurrentGroup()`) is purely local/client-side state.
- **Write idempotency** — all three writes are bounded by a 20s timeout (reads are still unbounded) and carry an **`idempotency_key` in the request body**, never a header: a payment is a transaction too, so they share one transport, and it matches how the rest of this API passes everything as body fields. `saveTransaction`/`savePayment` take a required `idempotencyKey` param and the service merges it into the body, so a call site cannot forget it. `savePayments` instead expects **every payment in the array to carry its own key** (the service asserts this), because per-item keys are what let a retry after a *partial* failure re-apply only the payments that did not land — a single key per request would only be safe if the server applied the batch atomically. Keys come from `lib/src/utils/idempotency.dart`: `IdempotencyKey` for single writes, scoped to a **form session** — stable across retries of the same payload, reissued when the payload changes, cleared only on success — and `IdempotencyKeySet` for batches, memoising a key per item identity (`from`/`to`/`amount` for settle-up; safe because the settlement walk advances both indices monotonically, so one debtor never pays the same creditor twice in a batch). Note the wire format itself is not covered by a test — the service calls top-level `http.post` with no injectable client, so there is nothing to mock. That combination is what makes retrying safe without swallowing an edited resubmission, and it is why `reset()` is never called on failure. **The server does not honour the key yet** — until it de-duplicates, this is preparation, not a guarantee. Because of that, the three write call sites distinguish `ApiException` (server answered, nothing committed → report its message) from any other error (no response → the write *may* have landed, so refresh the controllers and show `unconfirmedWriteMessage` rather than implying a clean failure). `test/idempotency_test.dart` pins the key lifecycle.
- `api_exception.dart` — every function throws `ApiException` (not a generic `Exception`) on a non-200 response; `apiExceptionFrom(response, fallback)` tries to pull a `message`/`error` field out of the JSON body and falls back to a plain-English default otherwise. `ApiException.toString()` returns just the message (no `"Exception: "` prefix), so it's safe to show directly in a `SnackBar`/`ErrorView`. Still no shared HTTP client wrapper or retry logic.

**Offline write gating** (`lib/src/utils/connectivity.dart`): there is no offline write queue — every mutation requires connectivity, so writes are blocked in two layers. `requireOnline(context, message:)` guards the request itself and is called in **every** write path (`new_expense.dart`, `new_payment.dart`, `settle_view.dart`, `new_form.dart` for person/join/create, `HomeViewState.handleInvite` for deep-link joins, and the leave-group menu item) — keep it even where the button is already disabled, because connectivity can drop while a form is open and pushed routes don't carry `HomeView`'s offline banner. `watchIsOnline(context)` drives the UI layer: offline disables "Settle up" (`overview_view.dart`) and the drawer's Join/Create group buttons, which also grow an explanatory caption since the drawer covers the banner. The FAB is the one exception to `onPressed: null` — a `FloatingActionButton` keeps its enabled colours when disabled, so offline it renders muted and tappable, showing the snackbar instead; note `floatingActionButtonLocation` must switch to `endFloat` at the same time, because `ExpandableFab.location` only positions the expandable FAB and leaves a plain one off-screen. Reads and local-only actions (switching groups, theme) stay available offline.

**Per-user transaction lists** (`lib/src/utils/expense_filters.dart`): `UserView`'s Expenses / Payments / Benefits-from rows open `ExpensesView`, which used to issue its own filtered `fetchExpenses` call per tap (a loader every time, broken offline). It now filters `AllExpenseController.expenses` in memory via `filterExpenses`, so those screens need no network at all. The predicates were **verified against the live backend** — for every user in a test group they returned the same transaction ids as the filtered endpoint and reproduced its `number_of_transactions`/`number_of_payments`/`number_of_benefits` counts, including the case where a received payment counts as a benefit:
- Expenses → paid by the user, excluding payments (`userId == id && !isPayment(e)`)
- Payments → paid by the user, payments only
- Benefits from → user appears in `distributions` (payments **not** excluded)

`isPayment()` lives here too and is the single definition of the `transactionTitle == 'payment'` convention — `expense_tile.dart` uses it, so the tile and the filter can't drift apart. `test/expense_filters_test.dart` pins all of this against the real backend's numbers. The counts shown in `UserView` still come from `UserBalance` (the backend), not from these predicates.

**Local caching** (`lib/src/services/cache_service.dart`): per-group `SharedPreferences` JSON blob cache for expenses and balances (`getCachedExpenses`/`setCachedExpenses`/`getCachedBalances`/`setCachedBalances`, plus `clearGroupCache`) — public wrappers over generic `_readList`/`_writeList` helpers, so adding another cached resource means one more wrapper, not another copy of the JSON plumbing. Reads are deliberately fault-tolerant: a cache entry that no longer parses (corrupt, or written by a build whose model shape has since changed) is **deleted and treated as a miss** rather than thrown, because an unguarded `fromMap` cast here would otherwise wedge the screen on every launch with no way to self-heal. Keep that try/catch if you touch this file. `CachedListController` reads the cache on cold start only (paint instantly if present, skip the full-screen spinner), then always still hits the network — on success the cache is overwritten and `isStale` clears; on failure, if data has already loaded (from cache or a prior fetch) it's kept and `isStale` is set instead of `isError`, so the UI degrades to "last known data" rather than blanking. This is a whole-list overwrite cache (matches the "backend always returns everything" networking model above), not an incremental/queryable store — if the backend ever gains a cursor param, or if list sizes grow enough to matter, revisit this as a real local DB (sqflite/drift) with per-row upserts, not just a drop-in storage-engine swap behind the same function signatures. `GroupsController.removeCurrentGroup()` calls `clearGroupCache` so a left group's cached data doesn't leak into a future rejoin.

**Models** (`lib/src/models/`): immutable `Equatable` classes with hand-written `fromMap`/`toMap`/`fromJson`/`toJson` (originally scaffolded from `models.jsonc` using the "JSON to Dart Model" generator — see that file for the intended workflow if adding new models). Field names in JSON are snake_case; model properties are camelCase.

**Navigation**: single named route (`/`) rendering `HomeView`; everything else is pushed imperatively (`Navigator.push`) from within views rather than declared as named routes. Deep links of the form `/joinGroup/<inviteId>` are handled specially in `lib/src/app.dart`'s `onGenerateRoute`, which calls back into `HomeViewState.handleInvite` via a `GlobalKey` to join a group and join it into `GroupsController`.

**Group-scoped UI**: `HomeView` is a two-tab (`Overview` / `Expenses`) scaffold for whatever group is currently selected in `GroupsController`; switching the selected group cascades through the proxy providers above to refetch overview/expense data.

**Push notifications**: OneSignal is initialized in `main.dart` with a hardcoded app ID; `GroupsController` tags the OneSignal user with `group: <name>` on join/leave so segments can be targeted per group. `HomeViewState` (`lib/src/views/home.dart`) registers `OneSignal.Notifications.addClickListener`/`addForegroundWillDisplayListener` in `initState()` (removed in `dispose()`) so a notification arriving or being tapped triggers `AllExpenseController.refresh()`/`UserBalanceController.refresh()` for whatever group is currently selected — this doesn't try to parse a `group_id` out of the notification's `additionalData`, since there's no backend code in this repo to confirm the payload shape; it's a deliberate simplification (worst case: one redundant refetch if the notification was for a different group than the one on screen). This matters more than it used to since the local cache (see "Local caching" above) means the app no longer refetches eagerly on its own — a notification is now one of the few signals that proactively refreshes stale data.

**Firebase**: initialized in `main.dart` for `firebase_core` only (config in `lib/firebase_options.dart`, generated by FlutterFire CLI from `firebase.json` — project `portfolio-rsaw409`). Regenerate rather than hand-edit if platform app IDs change. Web is **not** configured (`DefaultFirebaseOptions.currentPlatform` throws on the `chrome`/`web-server` device), so `flutter run` doesn't work on web. `flutter run -d macos` currently fails too, for an unrelated reason — `macos/Runner.xcodeproj`'s `MACOSX_DEPLOYMENT_TARGET` (10.15) predates what the installed Xcode/CocoaPods toolchain requires (12.0+); bump the deployment target project-wide to fix. Android is the only platform confirmed working in this environment; iOS wasn't tested here (no simulator available) but has no known issue.

**Theming** (`lib/src/theme/app_theme.dart`): `AppTheme.light` / `AppTheme.dark` build a Material 3 `ThemeData` from `ColorScheme.fromSeed(seedColor: Colors.deepPurple)`, with every component theme set (AppBar, Card, inputs, buttons, chips, dialogs, snackbars, FAB, tabs, etc.) so widgets should pull colors from `Theme.of(context).colorScheme` rather than hardcoding `Colors.*`. `AppSpacing`/`AppRadius` hold the 8dp spacing/radius scale used instead of magic-number `EdgeInsets`. `ColorScheme` is extended with `.positive` (a brightness-aware green) since M3 has no built-in "success" role — used opposite `.error` for the owed/owes balance coloring in `overview_view.dart`/`user_view.dart`.

**Shared UI components** (`lib/src/components/`): `async_state.dart` (`LoadingView`, `ErrorView`, `EmptyStateView`) is the standard loading/error/empty pattern for list views — pair with a controller's `isLoading`/`isError`/`errorMessage`. `expense_tile.dart` (`ExpenseTile`) is the shared row for both `all_expenses_view.dart` and `expenses_view.dart`. `detail_row.dart` (`DetailRow`) is the label/value row for detail screens (`single_expense_view.dart`, `user_view.dart`). `lib/src/utils/currency.dart` (`formatCurrency`) formats amounts as `₹1,234` via `intl` — used everywhere instead of ad hoc `'INR $amount'` string concatenation.

## CI/CD

`.github/workflows/android-release.yml` runs `flutter analyze` then `flutter test` on push/PR to `main`, builds a signed Android app bundle (keystore from secrets), and on pushes to `main` deploys to the Play Store **production** track (`developer.rohitsaw.split`) as a completed release.

**Versioning is not fully manual**: the workflow rewrites `pubspec.yaml` to `<version name>+${{ github.run_number }}` before building, so the `+N` you commit is overwritten and irrelevant — only the version *name* (e.g. `1.2.4`) needs bumping by hand. One latent caveat: because the code comes from the workflow's run number, recreating or renaming the workflow would reset it to 1 and Play would then reject uploads as non-increasing.
